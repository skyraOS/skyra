# Repository review — 2026-10-06

This is the pre-fix review. See [implementation and verification status](review-fixes-2026-10-06.md) for the subsequent changes.


Reviewed tracked checkout `a13330a`. This is a broad engineering review of the controller, interpreter, provider integration, browser, terminal and desktop clients, website, scripts, tests and documentation. It is not a formal security audit or a claim that every line has been exhaustively verified. Ignored historical worktrees, generated binaries, dependencies and local credentials are outside the reviewed source scope. No production source was changed.

**Assessment:** Skyra is a substantial research prototype with a coherent core architecture and real implementation behind its demonstrations. The separation of pure transitions from execution, explicit authority, OS enforcement, descriptor custody and reusable replay code are strong choices. It is not ready to carry the security and crash-recovery guarantees its strongest language suggests. There are reproducible failures in replay validation, ingress handling and concurrent procedure storage. The next milestone should be hardening and independent evaluation before another major feature expansion.

## Findings, in priority order

### 1. High — replay accepts a dependency that never completed

Source: [runtime/replay/replay.go](../controller/runtime/replay/replay.go), especially lines 142–185.

Replay checks a resolve's frame, round and inclusion of its predecessor. It does not require that predecessor to be a return or fault that actually discharged a slot. Its sibling checks compare waiting Horizons, but likewise do not establish terminal state. There is also no uniqueness check on the discharge list.

**Reproduced:** using the existing continuation fixture, I created a correctly hashed resolve immediately after the echo invocation, naming the invocation itself as the discharge. `Replay` accepted it with four records, without echo's return. A second probe named one actual discharge twice; replay accepted that too.

This is an audit-verification defect. It does not demonstrate that a sandboxed leaf can directly write runtime records, or that normal execution takes this invalid transition. It does demonstrate that an untrusted, internally hashed store can pass replay despite an impossible completion claim. That matters directly to the website verifier and the claim that replay defines correctness.

**Fix:** validate terminal state and the exact slot each discharge settles; reject duplicate discharges and duplicate slots; commit enough evidence of the emitted round to prove all expected children are represented. Reuse the runtime's semantic validation rather than accepting a resolve merely because it re-encodes consistently. Add adversarial store tests for premature, duplicated, omitted and unrelated discharges.

### 2. High — default ingress does not authenticate the human

Sources: [hosts/web/ws.go](../controller/hosts/web/ws.go), lines 22–56; [skyra](../skyra), `chat` and `tui_chat`; [hosts/web/main.go](../controller/hosts/web/main.go), `serveBrowser`.

The desktop supplies a bearer token. The default browser and terminal launch paths do not create one. With no token, the handshake accepts any client and ignores `Origin`. After upgrade, the client receives conversation state and can submit, open, close or delete conversations. A new connection also closes the prior client connection.

**Reproduced:** an unauthenticated request with `Origin: https://untrusted.example` received `101 Switching Protocols`.

Loopback binding limits network exposure but does not establish the caller's identity. Local processes can connect. An unrelated web page is not rejected at the application boundary; whether a specific browser allows its connection depends on that browser's local-network protections. I did not run a browser-based attack.

**Fix:** establish an authenticated session in every launch mode, validate browser origins and hosts, and support a browser-compatible credential flow. Simply requiring an Authorization header will break the current browser client, which cannot set that header through the native WebSocket constructor.

### 3. High — a small malformed WebSocket header can terminate the host

Source: [hosts/web/ws.go](../controller/hosts/web/ws.go), lines 59–97.

The peer supplies a 64-bit payload length that goes directly into `make([]byte, n)`, without a size limit or validation of the RFC high bit. `serveBrowser` has no panic recovery. Framing also does not enforce masking, FIN or reserved-bit rules.

**Reproduced:** a ten-byte header containing the maximum 64-bit length caused an allocation-length panic inside `readFrame`. The isolated probe recovered it to avoid killing the test process; the production goroutine does not. Large but allocatable lengths can also consume substantial memory. Authentication alone would not make authenticated malformed traffic safe.

**Fix:** bound frame/message size before allocation, reject malformed frames, bound handshake headers and read time, and use write deadlines. The TUI's frame reader already has a size bound. A maintained WebSocket implementation would reduce the amount of protocol behavior this project must defend itself.

### 4. Medium — concurrent interpreter stores collide on one temporary filename

Source: [interp/proc/proc.go](../controller/interp/proc/proc.go), lines 160–176 and `Store.Put`.

Every write to an object uses `<object>.tmp`. Independent procedures may share a content-addressed node, so concurrent writers truncate and rename the same temporary path. `Put` also checks for an existing procedure separately from publishing it, so its claimed one-representation rule is not an atomic claim.

**Reproduced:** 32 concurrent writes of different procedures sharing one node caused 24 failures, including `rename ...tmp ...: no such file or directory`. This is a filesystem race, which the normal Go race detector does not catch.

**Fix:** use unique temporary files and exclusive publication for immutable objects; verify existing objects; make procedure installation a write-once claim. Handle concurrent losers explicitly. Frame/refinement updates need their own ownership or synchronization rule.

### 5. Medium — procedure state lacks the runtime tree's durability protocol

Source: [interp/proc/proc.go](../controller/interp/proc/proc.go), `write`, `SetPosition`, `SetRemembering` and `SetRefinement`.

The store writes a file and renames it, without syncing the file or directory. The interpreter persists its position before emitting calls. Atomic visibility from rename is useful, but it does not guarantee that the position or installed procedure survives a machine crash after dependent runtime records become durable.

**Evidence:** code inspection. I did not simulate a power failure or establish the exact filesystem-specific loss sequence.

**Fix:** specify the durable ordering between actor state and emitted work, sync the necessary publications, and reconcile actor state against accepted records. Add crash-point tests before writing an operational restore guarantee. Existing `RecoverTree` work is useful evidence-reconciliation infrastructure, but explicitly does not revive frames or authorize repeating effects.

### 6. Medium — resume can fail after the host has accepted the message

Sources: [runtime/park/park.go](../controller/runtime/park/park.go), lines 133–144; [hosts/web/main.go](../controller/hosts/web/main.go), lines 307–320 and `watch`.

`park.Resume` reports success when `cmd.Start` succeeds, closes the host's descriptors and discards the eventual `cmd.Wait` result. The web host has already cleared its parked frame, marked the conversation pending and acknowledged the request. If the child starts but rejects its input or exits during handoff, the host's immediate error branch does not run. Its watcher refreshes activity but does not reconcile that pending conversation into failure.

Relatedly, several I/O failures in `instance.Drive` return directly after opening slots or beginning releases instead of becoming recorded custody faults. The tree can retain intent while the live product has no path that finishes or explains it.

**Evidence:** code inspection; no claim that every child failure is invisible, since normal target failures often become recorded faults.

**Fix:** acknowledge validated runtime custody, track later process failure, and reconcile unresolved work into an explicit recovery state. Do not automatically repeat external effects whose outcome is uncertain.

### 7. Medium — the mock's request guarantees exceed the real host's guarantees

Sources: [hosts/web/main.go](../controller/hosts/web/main.go), lines 260–269 and 418–431; [frontend/mock/check.mjs](../frontend/mock/check.mjs); [frontend/README.md](../frontend/README.md).

The mock checks that the same ID with different text is rejected as `conflict`, and that snapshots carry pending/returned request status. The real host stores only `map[string]bool`: any seen ID gets `accepted`, regardless of operation, conversation, text or incarnation. Production snapshots always contain an empty request ledger and null pending request ID.

**Reproduced:** a reused request ID on a different operation with the wrong incarnation still received `accepted`. Separately, all mock checks passed. That passing suite therefore does not verify the real implementation's claimed protocol.

The current path avoids duplicate execution within one host session, but can falsely acknowledge different work and cannot provide the documented ledger reconciliation.

**Fix:** either implement the agreed request identity/status model or revise the contract and clients together. Run the same behavioral suite against the real host with fake Codex. Keep mock behavior aligned with production, including the intentional policy that a normal agent fault permits the conversation to continue.

### 8. Medium — client drafts are cleared before delivery is established

Sources: [desktop/Sources/Skyra/Connection.swift](../desktop/Sources/Skyra/Connection.swift), `submit`, `open` and `send`; [frontend/components/Conversation.tsx](../frontend/components/Conversation.tsx), `send`.

The desktop's `send` returns true once the asynchronous send has been scheduled. The composer then clears the draft; a later transport error only sets a notice. The browser clears its composer immediately after sending too. Neither has a complete retained-message workflow tied to production request acknowledgement and reconciliation.

**Evidence:** code inspection. Host-restart handling preserves a pending opening draft in some cases, but does not cover all submitted-message failures.

**Fix:** retain submitted text and its request ID until acceptance is established; preserve it for explicit retry when delivery is unknown. Distinguish unknown delivery from a safe retry rather than blindly resending.

### 9. Lower priority — test entry points and current documentation are incomplete

Sources: [skyra](../skyra), line 369; [frontend/package.json](../frontend/package.json); [README.md](../README.md), lines 154 and 195; [controller/run.sh](../controller/run.sh).

`skyra test` omits the interpreter because it is a separate Go module. It also omits desktop, frontend and website checks. The standalone frontend lint command prompts to configure ESLint and exits unsuccessfully in this environment. There is no tracked CI workflow. Demo scenarios use `boot ... || true`, so a failed scenario can be hidden by an overall successful script exit.

The README's approximately 5,700 Go lines and 63 tests are stale: tracked Go/Python/Swift/TypeScript/shell files total about 29,750 lines including tests, and there are 181 Go test declarations under controller and TUI, including the nested interpreter. Its statement that fan-out is not built contradicts the current machine, tests and demo. The frontend README still specifies several predecessor semantics.

**Fix:** add one documented aggregate verification command and macOS CI, make demos check expected outcomes and replay success, configure lint explicitly, and separate current behavior from proposals/history.

## What is strong

- **Core architecture:** deterministic transitions, strict input fit, explicit narrowing and separate I/O form a coherent system. The standalone module boundary keeps CEL dependencies out of the runtime core. OS-level enforcement is implemented and exercised, not merely described.
- **Custody work:** explicit descriptor transfer, close-on-exec handling, acceptance receipts and write-once claims show serious attention to process boundaries and recovery evidence.
- **Testing:** useful semantic, tampering, sandbox, resident custody, protocol and renderer tests exist. The tracked Go suites pass under the race detector. The verified bugs are mostly missing adversarial cases, not evidence that the implementation is broadly nonfunctional.
- **Website:** using the actual Go replay engine in WebAssembly avoids a second verifier implementation. It is a good demonstration technique, although verifier defects propagate to it.
- **Clients:** shared protocol and consistent visual concepts across terminal, browser and native clients show product care. Desktop tests include actual rendering checks, and the TUI filters unsafe terminal control characters.

## Architectural limits and unproven claims

**Pure decisions do not remove distributed-systems problems.** Process-per-step reduces persistent in-memory state, but handoff acknowledgements, file publication, socket operations, actor state and external effects still have failure windows. The design needs explicit recovery semantics for each of them. “Intent was recorded” and “the operation's outcome is known” are different guarantees.

**The security boundary needs a written threat model.** Clarify trust in the operator registry, runtime executable, adapters, stateful actors, local users and ingress. The resident profile intentionally differs from ordinary Horizon grants; grants such as private provider state and credentials need to be documented as exceptions with evidence. Hashes establish consistency with trusted anchors; they do not independently authenticate an entire history supplied by someone else. Replay does not rerun external tools or prove that a recorded observation was truthful.

**Self-extension is substantive but currently constrained.** Remembered strands become procedures that compose registered capabilities. That is a real form of extension. It is not yet evidence that arbitrary newly authored executable tools work under the same guarantees. The README itself acknowledges that real Codex remembering and writing refinements still needs demonstration. Task-success, cost and interruption benefits need a baseline evaluation; code and demos alone do not settle the research question.

**Long-history cost is a concern, not a measured regression.** Continuations repeatedly receive accumulated steps; gathering revisits earlier rounds; replay prepends growing slices; the host scans record/horizon directories every 200 ms and broadcasts every conversation's complete history. Those costs deserve measurement at hundreds of turns and thousands of calls. Add paging, indexing or checkpoints after measuring, without undermining immutable audit evidence.

**Maintainability is becoming the limiting factor.** The 1,043-line machine, extensive transport-specific branching, duplicate Go/Python provider preparation, retained legacy adapters, multiple clients and many proposal documents create a large review surface. Some duplication intentionally isolates untrusted actors, which is defensible. A concise authoritative spec and parity tests would help more than another layer of abstractions. The visual work is well executed, but reliability and evaluation now warrant more attention than presentation.

**Additional hardening concerns:** runtime records use 0444 files and 0755 directories, so privacy depends on restrictive ancestor permissions on shared machines; stateful actors share their actor state across narrowed invocations; `Fchdir` changes process-global working directory; target output/stderr and several IPC bodies are insufficiently bounded; millisecond conversation IDs can collide during bursts. These are code-supported concerns, not reproduced privilege escapes or performance measurements. Prioritize them after the high findings and specify expected trust/concurrency assumptions.

## Recommended next milestone

1. Close replay's invalid-completion acceptance and secure/bound ingress.
2. Make interpreter publication concurrent-safe and define actor-state durability.
3. Make custody failure, request identity and unknown message delivery visible to clients.
4. Run one contract suite against the real host, include every module in an aggregate command, and enforce it in macOS CI.
5. Demonstrate real-model self-extension and publish a small adversarial and baseline evaluation before widening the product scope.

My honest judgment: the core idea is credible and the implementation has depth. The strongest work is the semantics and process-boundary design. The weakest area is the gap between those guarantees and the failure behavior at integration boundaries. Fixing that gap would materially strengthen both the software and the research argument.
